GRAPH-3361 filed 2026-07-29, reported by Ben Delarre in Slack #prj-graph-noderunners. Assigned to Chris Paterson (paterson), Epic Link GRAPH-1271 (SDK Developer Experience (DX) Enhancements).

**Problem:** Installing deps for a plugin in graph-plugins-core does not obey the platform major version of the plugin being built — a node plugin at `platformVersion: 2` resolves datatype plugin dependencies still at `platformVersion: 1`. Inspecting those datatype plugins shows they also carry the wrong major platform version, so the whole dependency chain can't resolve correctly.

**Why it's not fatal yet:** datatype plugins aren't actually loaded at runtime yet, so this currently only manifests as build warnings (repro: fresh clone of graph-plugins-core, install + build the `ml-nodes` package). Once runtime loading of datatype plugins lands this will break for real.

**Workaround found (does NOT fix root cause):** bumping `graph-sdk` to `2.11.9` and bumping `platform-exports` in both `ml-nodes` and `core-nodes` suppresses the build warnings, per Ben's testing with Mick Storm's PR. Ben explicitly confirmed the major version mismatch persists after this bump.

**How to apply:** Likely lives in graph-sdk's install/dependency-resolution logic — check how `platformVersionMajor` is used (or omitted) when resolving remote plugin dependencies. Related but distinct from [[jira_GRAPH-2978]] (submit-side resolvePlugin omits platformVersionMajor) — GRAPH-3361 is on the install/resolve side, not submit.

**Fixed (PR #3297, 2026-07-30):** `getTransitiveDependencies` in `project-plugins.ts` now passes `platformVersion` to `resolvePlugin()`, using the *dependency's own declared* `majorVersion` (not the requesting plugin's platform major — a platform-major-2 node plugin can legitimately depend on a still-major-1-published datatype plugin, since the datatype-plugin ecosystem hasn't migrated to platform-2 yet). Also added a private discovery-only cache key inside `getTransitiveDependencies` that folds in the *requesting* plugin's own platform major, so `.plugin-dependencies/` is now segmented `.plugin-dependencies/<platformMajor>/@scope/type-name/majorVersion/` — the same dependency resolved on behalf of two different-platform-major plugins no longer races/collides. This key is internal-only; `install.ts`/`dev-server.ts` still see the ordinary 2-part `ProjectPluginMapKey`.

**Blocked by a separate service bug, filed as [[jira_GRAPH-3363]]:** the ticket's own fix plan said `minor: 0` was a "safe floor," but live-testing against stage proved the opposite — `graph-services`' `plugins-resolve.ts` controller treats `minor: 0` as a literal ceiling (`resolvedMinor(1) > requestedMinor(0)` → 404) even though the SQL model layer (`findHighestVersion`) correctly treats falsy `0` as "no restriction." GRAPH-3361's fix ships as designed regardless (matches the ticket's intended semantics and is unit-tested), but full end-to-end resolution won't succeed until GRAPH-3363 lands server-side.

**Scope expanded twice more post-merge-review (2026-07-30), both user-directed:**
1. `PluginService.resolvePlugin`/`listPlugins`/`batchResolvePlugins` (`graph-plugin-services-client`) now require `platformVersion` and narrow its type to major-only (`PlatformMajorVersion { major: number }`) — server-side minor filtering is unreliable (GRAPH-3363) so the client never sends it. New shared `PlatformMajorVersion` type in `graph-plugin-types`. Cascaded into `submit.ts` (getPlatformVersion/getPluginStatus simplified to major-only — nothing in graph-sdk read `.minor` anymore) and `make-docs.ts` (its `listPlugins()` call had no platform-version context; now derives one from the first target plugin's own manifest, since it's only used for LLM few-shot examples).
2. **Platform-major chain mismatch is now a hard error**, not just scoped-resolution: if a resolved dependency's own `platformVersionMajor` doesn't match the platform major of whichever plugin depends on it — at ANY edge in the transitive chain, not just the root — `getTransitiveDependencies` throws (`visit()` threads `{name, platformMajor}` of the requesting plugin down through recursion). User explicitly accepted that this breaks `ml-nodes`/`core-nodes` today: confirmed live against **production** registry data — `@adobe/node-entity-segmentation` (platform major 2) → `@adobe/datatype-mask` (platform major 1) throws exactly as designed. Most platform-major-2 node plugins in ml-nodes currently depend, directly or transitively, on datatype/widget/utility plugins not yet republished for platform major 2 — their install/build will fail until migrated. This is intentional, not a regression.

All changes are on PR #3297 (branch `paterson/GRAPH-3361/fix-datatype-plugin-platform-version`), 4 commits as of 2026-07-30.

**Known latent gap in the shipped fix (found 2026-07-31, deferred on purpose):** `resolveExternal`'s `dependencyPlatformVersion.major` uses `depSpec.majorVersion` (the dependency's own *package* major, from the manifest's `dependencies` entry) as the `platformVersion.major` sent to `resolvePlugin`. That's conceptually wrong — package major and platform major are independent axes; the manifest carries zero platform-version info about a dependency. The technically correct value is the *requester's own* platform major (already computed as `requestingPlatformMajor`, just not used for the query). It only "works" today because package-major and platform-major happen to coincide numerically for every currently-published datatype/widget/utility plugin. User explicitly chose not to fix this yet (2026-07-31) — using the requester's major instead would turn today's clear "platform version mismatch" chain error into a raw, less-informative registry 404 for the exact same real-world break (ml-nodes), unless a fallback diagnostic fetch is added. Revisit if/when a plugin's package major and platform major actually diverge.

This came up while building `packages/graph-sdk/docs/2026-07-31-platform-version-dependency-resolution.md` — a mermaid-diagram doc explaining the install-time dependency resolution flow to Sayash Kumar (Plugin Service team), who didn't have SDK context in the Slack thread `C0BHUBYUZDL` (thread ts `1785374665.789929`) discussing GRAPH-3361/3363.

**Team agreed on a concrete server convention (2026-07-31):** instead of omitting `platformVersion` or sending `0`, always send an explicit `platformVersion: -1` sentinel meaning "match on platform major only." Shipped client-side (`PLATFORM_MINOR_MATCH_ANY = -1` constant in `plugin-service.ts`, sent unconditionally by `resolvePlugin`/`listPlugins`/`batchResolvePlugins`; `project-plugins.ts`'s vestigial `minor: 0` removed). [[jira_GRAPH-3363]] revised to track this as the concrete server-side ask. All builds/lint/tests green across `graph-plugin-services-client`, `graph-sdk`, `graph-plugins`.

**GRAPH-3363 confirmed fixed on stage + prod (2026-08-04)** — [[jira_GRAPH-3363]] no longer blocks. Live-verified via raw HTTP probes and a full `graph-sdk install` against `ml-nodes` on both environments: resolution now succeeds end-to-end; installs correctly stop only at genuine platform-major chain mismatches (this ticket's own intentional hard error), not at 400s/404s from minor-version handling. PR #3297 is functionally complete pending final review/merge.
