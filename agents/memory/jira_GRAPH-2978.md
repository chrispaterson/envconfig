GRAPH-2978: `getPluginStatus()` in `src/commands/submit.ts:616-635` calls `pluginService.resolvePlugin()` without a `platformVersion`, so the service defaults the lookup to `platformVersionMajor: 1`. Any plugin only published under a newer platform major (e.g. 2) resolves as "not found," so `submit.ts:267` treats it as brand new and forces `updateType = "major"` every submission — a chain reaction that bumped `video-frame` 1→2→3 and blocked plugins-prod PRs #3824/#3825.

**Why:** Diagnosed 2026-07-16 in Slack thread https://adobe-3di.slack.com/archives/C084XR5E92N/p1784228617242849 by Ron De Benedetti, Ben Delarre, Patricio Gonzalez Vivo, Chris Paterson, Sayash Kumar. This is the short-term SDK-side fix; separate follow-ups discussed in the same thread (not yet filed): services should require `platformVersionMajor` on resolve rather than defaulting it, and longer-term the team wants to stop server-computed version bumps entirely and use `manifest.json`'s version as source of truth (needs a migration script backfilling manifest.json from published DB versions).

**How to apply:** Fix is to pass the plugin's actual `platformVersionMajor` into the `resolvePlugin` call at `submit.ts:625`. Linked to Epic GRAPH-2458 (Package Submission), added to active sprint (Graph Sprint 25, 7/13-7/24). As of ticket creation, submitting/merging plugin updates to stage was NOT confirmed safe — Chris told Jeremy Biddle to hold off.

**Status (2026-07-16): Fixed and committed on branch `paterson/GRAPH-2978/fix-resolveplugin-platform-version-major`** (commit `1f4c7c426` "Pass platform version to resolve endpoint", plus a rush change file). Added a `getPlatformVersion(manifest)` helper in `submit.ts` that derives `{ major, minor }` from `manifest.platformVersionMajor ?? normalizePlatformVersion(manifest.platformVersion).major` (same idiom already used in `build.ts:490-491`). Threaded a new required `platformVersion` param through `getPluginStatus()` and both call sites: the main submission loop (uses `plugin.manifest`) and the `--status` fast path (previously had no `ProjectPlugin` in scope at all — now calls `getProjectPlugins({ pluginNames: [pluginName] })` first and throws `Plugin ${pluginName} not found in project` if absent). Added a regression test asserting `resolvePlugin` is called with the plugin's declared platform major (2) rather than being omitted. Build/lint/test all pass (504 tests).

**Known design debt introduced by this fix:** Plugin discovery (`extractPlugin`, per GRAPH-2302) already does a one-way conversion of manifest.json's `platformVersion` field (legacy number, or `{major,minor}` object) into flat fields on `ProjectPlugin.manifest`: `platformVersion` (minor) + `platformVersionMajor` (major). This fix's `getPlatformVersion()` helper converts those flat fields *back* into a `{major,minor}` object to satisfy `resolvePlugin`'s `PlatformVersion` param — i.e. discovery flattens it, and now submit re-combines it. This round-trip is acceptable for the bug fix but is not a good long-term shape. Chris flagged that a better solution is needed later (e.g. carry the combined `PlatformVersion` object on `ProjectPlugin` directly rather than flattening at discovery time, or have the service client accept the flat fields) — revisit when touching this area again, and don't be surprised if the flatten/re-combine round-trip goes away in a future refactor.
